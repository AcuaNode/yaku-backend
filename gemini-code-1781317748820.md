# Tarea: Desacoplamiento Arquitectónico de Equipment y Telemetry (Monolito a Microservicios)

## Contexto del Problema y Objetivo
Necesitamos evaluar las lecturas de sensores (temperatura, pH) contra umbrales específicos de calidad de agua, los cuales dependen de la especie asignada a cada estanque (`Pond`). 

Para mantener la autonomía de los módulos y facilitar una futura migración a microservicios independientes, el módulo `Telemetry` debe ser el encargado de ejecutar las reglas de negocio y alertas sin conocer la estructura interna, entidades o base de datos del módulo `Equipment`. Aplicaremos el **Principio de Inversión de Dependencias**.

---

## Guía de Implementación Lógica por Pasos

### Paso 1: Definir el Contrato de Abstracción (Módulo Telemetry)
Debes crear un punto de acoplamiento abstracto (Interfaz) dentro de la capa de dominio/servicio de `Telemetry`. Este componente define *qué* información necesita telemetría, delegando el *cómo* se obtiene a las capas externas.

- **Ubicación:** Capa de servicios/puertos de `Telemetry`.
- **Lógica requerida:** - Debe definir una función/método que acepte como parámetro único el identificador del estanque (`pondId`).
  - Debe retornar una cadena de texto plana (`String`) que represente el nombre de la especie (ej. "TRUCHA", "TILAPIA").
- **Regla estricta:** Este archivo no debe importar ninguna clase, entidad ni repositorio perteneciente a `Equipment`.

### Paso 2: Implementar la Fachada de Datos (Módulo Equipment)
El módulo `Equipment` es el dueño de la verdad sobre los estanques. Aquí debes implementar el contrato definido en el Paso 1 para resolver la petición en memoria mientras coexistan en el mismo monolito.

- **Ubicación:** Capa de infraestructura o adaptadores de `Equipment`.
- **Lógica requerida:**
  - Debe implementar la interfaz creada en `Telemetry`.
  - Debe inyectar el repositorio nativo de estanques (`PondRepository`).
  - Al recibir el `pondId`, debe buscar en la base de datos la entidad `Pond`, extraer el campo de texto que almacena la especie y devolverlo.
  - Debe manejar excepciones de negocio en caso de que el identificador del estanque no exista.

### Paso 3: Estructurar el Modelo de Reglas y Umbrales (Módulo Telemetry)
`Telemetry` debe ser el dueño absoluto de los parámetros de control ambiental. Necesitamos persistencia independiente para mapear especies con rangos ideales.

- **Ubicación:** Capa de dominio y persistencia de `Telemetry`.
- **Lógica del Modelo:**
  - Define una estructura/tabla de datos para los Umbrales (`Threshold`).
  - Atributos lógicos: Identificador de especie (String que actuará como llave de búsqueda), límites mínimos y máximos para temperatura, y límites mínimos y máximos para pH.
- **Lógica del Repositorio:**
  - Debe permitir consultas basadas estrictamente en el nombre de la especie (String) para recuperar sus límites operativos.

### Paso 4: Construir el Motor de Evaluación de Alertas (Módulo Telemetry)
Modifica o implementa el servicio que procesa la ingesta de datos de los sensores para orquestar la validación utilizando los componentes anteriores.

- **Ubicación:** Capa de aplicación de `Telemetry`.
- **Flujo Lógico Secuencial:**
  1. **Recepción:** El servicio es invocado cuando llega una nueva lectura de sensor (contiene `pondId`, `temperature`, `ph`).
  2. **Resolución de Identidad:** Invoca la interfaz de abstracción (Paso 1) pasando el `pondId` para obtener el nombre de la especie.
  3. **Carga de Reglas:** Con el nombre de la especie recibido, consulta el repositorio de umbrales (Paso 3) para obtener sus rangos mínimos y máximos.
  4. **Evaluación de Negocio (If/Else):**
     - Si la temperatura actual es menor al mínimo o mayor al máximo establecido, marca la lectura como estado anómalo.
     - Si el pH actual viola los rangos permitidos, marca la lectura como estado anómalo.
  5. **Despacho Dinámico:** Si se viola alguna regla, construye un mensaje descriptivo que incluya el valor erróneo, el límite violado y el tipo de peligro (`WARNING` o `CRITICAL`), y envíalo al servicio de notificaciones (FCM).

---

## Criterios de Aceptación para el Agente
1. **Fronteras Limpias:** No debe existir ningún `import` en el paquete de `Telemetry` que apunte a los modelos, entidades o repositorios de `Equipment`.
2. **Modularidad:** El código debe quedar listo para que, en el futuro, la implementación del paso 2 pueda reemplazarse por un cliente HTTP (Feign/WebClient) sin alterar la lógica del paso 4.
3. **Manejo de Errores:** Si un estanque no tiene una especie válida o no existen umbrales configurados para ella, el sistema debe registrar un log de advertencia o lanzar una excepción controlada en lugar de caer en un `NullPointerException`.
